Digital-to-Analog Converter (DAC)
#################################

Overview
********

A Digital-to-Analog Converter (DAC) turns a digital code written by software into an analog output
level, usually a voltage on a device pin that is proportional to the code and to the reference
voltage of the converter.

The DAC API provides a generic method to interact with DAC peripherals, whether they are integrated
in the SoC or attached externally over a bus such as I2C or SPI. A DAC device exposes one or more
output channels: the application configures a channel once, then writes raw output codes that the
hardware holds until the next write. Drivers implement :c:struct:`dac_driver_api`, which consists
of two mandatory operations, channel setup and value write. Key concepts include:

**DAC Channels**
  Each channel is an independent output path identified by a small integer,
  :c:member:`dac_channel_cfg.channel_id`, whose mapping to a physical output is defined by the
  driver and the devicetree.

**Channel Configuration**
  :c:struct:`dac_channel_cfg` describes the resolution of the codes written to a channel and two
  hardware dependent output options, :c:member:`dac_channel_cfg.buffered` and
  :c:member:`dac_channel_cfg.internal`. It is applied with :c:func:`dac_channel_setup`.

**Raw Values**
  :c:func:`dac_write_value` sets the output of one channel to a raw code in the range allowed by the
  configured resolution. Helpers such as :c:func:`dac_millivolts_to_raw` convert a voltage into the
  corresponding code.

**Devicetree Integration**
  DAC controllers and their channels are described in devicetree. Applications reference a channel
  through an ``io-channels`` property and collect everything needed to use it in a
  :c:struct:`dac_dt_spec`, populated with :c:macro:`DAC_DT_SPEC_GET` or one of its variants.

DAC Channels
************

A channel must be configured with :c:func:`dac_channel_setup` (or :c:func:`dac_channel_setup_dt`)
before any value is written to it. The function takes a :c:struct:`dac_channel_cfg` with the
following fields:

**channel_id**
  Identifier of the channel within the DAC device. The numbering is device specific: the STM32
  driver numbers its channels starting at 1, while single-output devices such as the NXP LPDAC
  accept only channel 0. Configuring a channel the driver does not implement fails with ``-EINVAL``
  or ``-ENOTSUP``.

**resolution**
  Number of bits of the codes written to the channel. A driver accepts only the resolutions its
  hardware supports (for example 8 or 12 bits on STM32) and returns ``-ENOTSUP`` for other values.

**buffered**
  Enables the output buffer (amplifier) of the channel, which is needed when the output pin drives a
  load directly without an external amplifier. The exact effect is hardware dependent, and DACs
  without an output buffer may reject the flag.

**internal**
  Routes the channel output to on-chip peripherals through an internal path instead of the device
  pin, on SoCs that support such connections. Drivers for external DACs reject the flag with
  ``-ENOTSUP``, and on some SoCs ``internal`` and ``buffered`` are mutually exclusive.

Writing Values
==============

:c:func:`dac_write_value` (or :c:func:`dac_write_value_dt`) sets the output of a channel to an
unsigned code between 0 and ``2^resolution - 1``; drivers return ``-EINVAL`` when the value does
not fit the configured resolution. The call is synchronous, and the API has no asynchronous write,
completion callback or hardware trigger interface: waveforms are generated by writing successive
codes from application code, as the :zephyr:code-sample:`dac` sample does for a sawtooth signal.

Drivers for devices that can update all outputs at once (for example the TI DACx311 and DACx3608
drivers) accept :c:macro:`DAC_CHANNEL_BROADCAST` as the channel argument of
:c:func:`dac_write_value` once at least one channel has been configured. The identifier is not
valid for :c:func:`dac_channel_setup`.

Converting Voltages to Raw Values
=================================

:c:func:`dac_millivolts_to_raw` and :c:func:`dac_microvolts_to_raw` compute the code that produces
a given voltage from the reference voltage of the channel (in millivolts) and its resolution. They
return ``-ERANGE`` and leave the value untouched when the result is out of range for the
resolution. The :c:func:`dac_millivolts_to_raw_dt` and :c:func:`dac_microvolts_to_raw_dt` variants
take both parameters from a :c:struct:`dac_dt_spec`, which requires the ``zephyr,vref-mv`` property
to be set in the channel node. These helpers are the counterpart of the raw-to-voltage helpers of
the :ref:`ADC API <adc_api>`.

Devicetree Configuration
************************

DAC controller bindings include :zephyr_file:`dts/bindings/dac/dac-controller.yaml`. A controller
node carries a ``#io-channel-cells`` property that tells how many cells follow the controller
phandle in an ``io-channels`` reference. Most controllers use one cell, named ``output``, holding
the channel identifier (the STM32 SoC devicetrees define ``dac1`` with ``#io-channel-cells = <1>``);
controllers with a single output may declare zero cells, in which case channel 0 is implied.

Channel properties are given in child nodes of the controller, which must be named ``channel`` and
use the channel identifier as their unit address. The child binding defines ``zephyr,resolution``,
``zephyr,buffered``, ``zephyr,internal`` and ``zephyr,vref-mv``, mirroring
:c:struct:`dac_channel_cfg` plus the reference voltage used by the conversion helpers. An
application typically enables the controller, describes the channel it uses and references it from
the :ref:`/zephyr,user <dt-zephyr-user>` node in a board overlay:

.. code-block:: devicetree

   / {
       zephyr,user {
           io-channels = <&dac1 1>;
           io-channel-names = "dac1";
       };
   };

   &dac1 {
       status = "okay";
       #address-cells = <1>;
       #size-cells = <0>;

       channel@1 {
           reg = <1>;
           zephyr,resolution = <12>;
           zephyr,buffered;
           zephyr,vref-mv = <3300>;
       };
   };

Basic Operation
***************

Typical use of the DAC API is:

#. Describe the channel in devicetree and obtain a :c:struct:`dac_dt_spec` with
   :c:macro:`DAC_DT_SPEC_GET`, :c:macro:`DAC_DT_SPEC_GET_BY_NAME` or
   :c:macro:`DAC_DT_SPEC_GET_BY_IDX`; the ``_OR`` variants expand to a default value when the
   ``io-channels`` reference is missing.
#. Check that the device is ready with :c:func:`dac_is_ready_dt`.
#. Configure the channel once with :c:func:`dac_channel_setup_dt`.
#. Convert the desired voltage to a raw code, if needed, with :c:func:`dac_millivolts_to_raw_dt`.
#. Write the code with :c:func:`dac_write_value_dt`, and repeat whenever the output must change.

The ``_dt`` helpers require the channel child node. Without it,
:c:member:`dac_dt_spec.channel_cfg_dt_node_exists` is false and :c:func:`dac_is_ready_dt` returns
``false``, while :c:func:`dac_channel_setup_dt`, :c:func:`dac_write_value_dt` and the conversion
helpers return ``-ENOTSUP``.

.. code-block:: c
   :caption: Configure a DAC channel from devicetree and set its output to half scale

   #include <zephyr/drivers/dac.h>

   static const struct dac_dt_spec dac_out =
       DAC_DT_SPEC_GET_BY_NAME(DT_PATH(zephyr_user), dac1);

   int dac_output_init(void)
   {
       int err;

       if (!dac_is_ready_dt(&dac_out)) {
           return -ENODEV;
       }

       err = dac_channel_setup_dt(&dac_out);
       if (err < 0) {
           return err;
       }

       return dac_write_value_dt(&dac_out, (1U << dac_out.channel_cfg.resolution) / 2);
   }

To output a specific voltage instead, store it in millivolts in a ``uint32_t``, convert it in place
with :c:func:`dac_millivolts_to_raw_dt`, and write the result with :c:func:`dac_write_value_dt`.

The API can also be used without :c:struct:`dac_dt_spec`: obtain the controller with
:c:macro:`DEVICE_DT_GET`, fill a :c:struct:`dac_channel_cfg` in code (or with
:c:macro:`DAC_CHANNEL_CFG_DT` from a channel node) and call :c:func:`dac_channel_setup` and
:c:func:`dac_write_value` directly. The :zephyr:code-sample:`dac` sample follows this approach,
taking the controller, channel identifier and resolution from custom ``/zephyr,user`` properties.

Usage Constraints
*****************

* :c:func:`dac_channel_setup` and :c:func:`dac_write_value` are system calls, so user mode threads
  can use them once they have been granted access to the device object (see :ref:`usermode_api`).
  The ``_dt`` helpers are inline wrappers around these calls, and the conversion helpers are
  plain inline functions that do not access the device.
* The API does not define behavior when called from interrupt context. Drivers for external DACs
  perform I2C or SPI transfers inside :c:func:`dac_write_value`, so calls should be made from
  thread context.
* The API does not serialize concurrent callers. Some drivers, such as the emulated DAC
  (:dtcompatible:`zephyr,dac-emul`, :kconfig:option:`CONFIG_DAC_EMUL`), protect their channel
  state with a mutex; applications that share a device between threads should synchronize them.
* Writing to a channel that has not been configured is not supported, and the result is driver
  specific (the emulated DAC returns ``-ENXIO``).
* The API has no power management calls of its own. Drivers that support device power management
  (for example the Silicon Labs VDAC driver) integrate with the :ref:`pm-guide` framework.
* Many drivers register their device at :kconfig:option:`CONFIG_DAC_INIT_PRIORITY`, which defaults
  to ``KERNEL_INIT_PRIORITY_DEVICE``.

Shell Commands
**************

When :kconfig:option:`CONFIG_DAC_SHELL` is enabled, the ``dac`` command is available in the
:ref:`shell <shell_api>` to configure channels and set output levels interactively, without writing
application code. Each subcommand takes the DAC device name as its first argument; device names can
be tab-completed, and numeric arguments accept decimal or ``0x``-prefixed hexadecimal values.

``dac setup <device> <channel> <resolution> [-b] [-i]``
  Configure ``channel`` with the given resolution by calling :c:func:`dac_channel_setup`. ``-b``
  enables the output buffer and ``-i`` connects the channel internally, setting the corresponding
  :c:struct:`dac_channel_cfg` flags.

``dac write_value <device> <channel> <value>``
  Write a raw value to ``channel`` with :c:func:`dac_write_value`.
