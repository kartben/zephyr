Zephyr POSIX Performance Audit

A measured pass over the POSIX compatibility layer — pthread primitives, the fd table, eventfd, poll/select, and the BSD socket hot paths — with ten fixes implemented, benchmarked, validated, and staged one per branch.

base 8dafb9a89 (main) date 2026-08-25 method callgrind instruction counts, native_sim/native/64 validation twister: native_sim + qemu_x86_64

01Method

Deterministic instruction counts instead of noisy wall-clock timing.

A dedicated benchmark application exercises 32 hot paths (mutex/sem/cond ops, clock reads, eventfd, fd read/write dispatch, poll() at 1/4/16/32 descriptors, UDP/TCP loopback send+receive, mqueue, nanosleep) through Zephyr's own POSIX implementation — built with minimal libc so the host glibc is not accidentally measured, with fd/socket paths entering through the zvfs_*/zsock_* symbols that the POSIX wrappers alias. Each phase brackets a 500–2000-iteration loop with callgrind client requests, giving exact per-phase dumps; per-function inclusive instruction counts divided by iteration count are the reported metric. Callgrind counts are deterministic, so deltas of a few instructions are real, not noise; they model CPU cost, not memory-hierarchy or wall-clock effects.

Reference points from the baseline: k_mutex lock+unlock costs 194 instructions, POSIX sem_wait+sem_post only 15 more than raw k_sem (a wrapper done right), while pthread_mutex lock+unlock cost 455 — 261 instructions of compatibility-layer overhead. That gap is what this audit attacks.

03Findings in detail

F1 — Every pthread object operation took a spinlock just to validate a handle

posix-lockfree-obj-validation · lib/utils/bitarray.c, subsys/portability/posix/options/{mutex,cond,rwlock,spinlock,barrier,key}.c

Path
pthread_mutex_lock() → to_posix_mutex() → get_posix_mutex() → sys_bitarray_test_bit() — and the same shape for cond, rwlock, spinlock, barrier and key objects, on every operation.
Why slow
Handles are pool indices; each op re-validates the allocation bit through sys_bitarray_test_bit(), which takes and releases the bitarray spinlock (IRQ mask/restore on UP, atomic RMW + barriers on SMP) plus a divide/modulo — around 50 instructions to read one bit of one aligned word. The lock adds no safety: the result is stale on return, and the only misuse it detects is undefined behavior per POSIX anyway. Measured at 103 of the 455-instruction mutex pair.
Fix
New sys_bitarray_test_bit_nolock() — same bounds checks, single aligned word read, documented staleness contract — used by the six POSIX validation sites. Allocation/free/mutation keep full locking. Unit test extended to cover the new API (in-range, out-of-range).
Measured
pthread_mutex lock+unlock: 455 → 337 (-26%; wrapper overhead 261 → 143, -45%) pthread_cond_signal: 177 → 118 (-33%) pthread_getspecific: 378 → 319 (-16%)
Correctness
Bit reads are single aligned word accesses (atomic on all supported architectures). Racing a destroy is UB per POSIX either way; the locked test could not detect a destroyed-and-reused slot either. Two IRQ-lock windows removed per mutex pair.
Testing
twister: threads_base, semaphores, rwlocks, spinlocks, barriers on qemu_x86_64 (16/16 configs, 138/138 cases) + tests/kernel/common incl. the new bitarray API test (12/12 configs, 944/944 cases, native_sim + qemu_x86_64).
Trade-offs
+1 small function of flash when used; API surface grows by one documented accessor.

F2 — pthread_once serialized on the global pool lock forever

posix-once-fast-path · subsys/portability/posix/options/pthread.c

Why slow
Every call — for the life of the program — took pthread_pool_lock to read one boolean that can never return to false. Lazy-init guards in library code pay this per call, and contend with unrelated pthread operations.
Fix
Return immediately when the flag is already observed set; the slow path is unchanged.
Measured
pthread_once (hot): 244 → 21 (-91%)
Correctness
Identical to the locked path, including its pre-existing quirk: the flag is set before init_func() runs, so a concurrent caller could already return before init completes (see bug B1 below). The fast path neither fixes nor worsens that.
Testing
twister threads_base on qemu_x86_64 (3/3 configs, 108/108 cases).

F3 — eventfd rebuilt its fd from the object with O(open fds) scans, once under a spinlock

zvfs-eventfd-drop-fd-scans · lib/os/zvfs/zvfs_eventfd.c

Path
zvfs_eventfd_read(fd) → zvfs_get_fd_obj() → zvfs_get_obj_lock_and_cond(obj) → linear fdtable scan; blocking ops repeated the scan inside k_spin_lock(&efd->lock) — an O(N) walk with interrupts masked.
Why slow
The reverse obj→fd scan recovered the per-fd lock/condvar the caller effectively already had. Cost scales with fd number and table size (ZVFS_OPEN_SIZE is 40+ in Wi-Fi builds, and wpa_supplicant's event loop is eventfd-based).
Fix
Implement the existing ZFD_IOCTL_SET_LOCK ioctl (the socket layer's mechanism) to cache the fd-entry mutex at creation, and embed the blocking-wait condvar in struct zvfs_eventfd. All three scans gone; the #99234 hold-the-mutex-exactly-once protocol is preserved.
Measured
zvfs_eventfd_read: 496 → 430 (-13% at fd 4; scan was O(fd)) zvfs_eventfd_write: 494 → 430 (-13%)
Testing
twister eventfd + socket poll/select suites, native_sim + qemu_x86_64 (6/6 configs, 54/54 cases).
Trade-offs
+1 pointer and one k_condvar (~12–24 B) per eventfd instance.

F4 — eventfd re-raised already-signaled poll signals on every operation

zvfs-eventfd-skip-redundant-raise · lib/os/zvfs/zvfs_eventfd.c

Why slow
Each read raised write_sig and each write raised read_sig unconditionally. The signal is usually already set, so k_poll_signal_raise() took the kernel-global poll spinlock to store a value that was already there and walk an empty list.
Fix
Skip the raise when the signal is signaled and its wait queue is empty. Safe because signals are only mutated under efd->lock and k_poll never registers a waiter on an already-met condition — while signaled, the queue can only shrink. The list-non-empty case still raises (k_poll_signal_raise wakes exactly one waiter per call, so serial wakes for multiple pollers are preserved).
Measured
read() on eventfd: 452 → 392 (-13%) zvfs_eventfd_read: 496 → 436 (-12%) needed-raise side: +3 instructions for the check
Testing
twister eventfd + socket poll/select suites, native_sim + qemu_x86_64 (6/6 configs, 54/54 cases).

F5 — Every UDP/TCP send re-registered the receive callback

net-sockets-skip-recv-rereg · subsys/net/lib/sockets/sockets_inet.c

Path
zsock_sendto_ctx() → net_context_recv() → recv_dgram() → bind_default() + net_conn_update(), per datagram: a context mutex pair, a zeroed sockaddr_storage on stack, callback rewrite, and two sockaddr memcpys into the connection table.
Why slow
Registration only matters for the first send on an unbound socket; bind()/connect()/accept() re-register themselves. Every subsequent send repeated a ~500-instruction no-op. (zsock_sendmsg_ctx() never did this — evidence it is not fundamental.)
Fix
Skip when zsock_received_cb is registered and a connection handler exists. Offloaded contexts never set conn_handler, keeping their per-send behavior. Does not reintroduce the #70020 unregister/re-register race — the update is skipped only when it would write identical values.
Measured
zsock_sendto_ctx (UDP 32 B): 9955 → 9523 (-4.3%) net_context_recv per send: 431 → 0 k_mutex ops per send+recv round: one pair fewer
Testing
twister tests/net/socket/udp + tcp on native_sim (14/14 configs, 624/624 cases).

F6 — Send/receive timeouts fetched through a mutex-guarded 25-case switch

net-sockets-lockfree-timeo · subsys/net/lib/sockets/sockets_inet.c

Why slow
Every blocking send and recv called net_context_get_option() — context mutex lock/unlock plus an option switch — to load one k_timeout_t. The per-socket fd mutex already serializes these paths against setsockopt(), so the inner lock protected nothing for socket users.
Fix
Small static helpers read ctx->options.sndtimeo/rcvtimeo directly (K_FOREVER when the option is compiled out). getsockopt/setsockopt and external net_context users keep the locked accessor.
Measured
zsock_sendto_ctx (UDP 32 B): 9955 → 9559 (-4.0%) kernel mutex work per UDP send+recv round: -11.6% (two pairs fewer)
Testing
twister tests/net/socket/udp + tcp + misc on native_sim (18/18 configs, 672/672 cases).

F7 — Every received datagram scanned the whole context table

net-context-o1-conn-context · subsys/net/ip/net_context.c

Why slow
net_context_packet_received() resolved conn→context with find_context(), a linear scan of contexts[] comparing handler pointers, per delivered UDP/RAW packet — although conn->context has stored the answer since registration.
Fix
Use conn->context with the same validity checks the scan performed (in-use, still the current handler).
Measured
per delivered datagram: 864 → 854 (-1.2% at default NET_MAX_CONTEXTS=6)
Honest framing: small at the default table size; the point is the RX fast path no longer scales with CONFIG_NET_MAX_CONTEXTS.
Testing
twister tests/net/context + socket/udp + socket/tcp on native_sim (15/15 configs, 639/639 cases).

F8–F10 — Small provable wins: mutex fast path, rwlock clock read, nanosleep clock read

posix-mutex-fast-path · posix-rwlock-lazy-uptime · clock-nanosleep-fewer-reads

F8
acquire_mutex() called k_current_get() (a syscall in userspace builds without TLS current) and loaded the mutex type before checking whether the mutex is even owned. Reordered: 241 → 229 instructions (-5%) on native; one syscall saved per uncontended lock in userspace builds.
F9
write_lock_acquire() read k_uptime_get() unconditionally to prorate a timeout that untimed wrlock and trywrlock never use; trylock paid a second read to compute an always-zero remainder. Both reads now happen only for finite non-zero timeouts. Validated: rwlocks suite on qemu_x86_64 (3/3 configs, 9/9 cases).
F10
sys_clock_nanosleep() re-read the clock after every completed sleep just to conclude no time remains. Using k_sleep_ticks()'s return removes one spinlocked 64-bit tick read per completed sleep (the common case); early-wakeup re-sleep behavior unchanged. The zero-length path measures -3%; the saved read on real sleeps is the actual win. Validated: timers + clock_selection suites on qemu_x86_64 (6/6 configs, 60/60 cases).

04Bugs found along the way

Not performance issues — correctness problems the audit surfaced. Reported here rather than silently patched, since each needs a maintainer conversation.

  • B1  pthread_once can return before init completes. The flag is set before init_func() runs (outside the lock), so a second thread calling pthread_once() concurrently returns immediately while the initializer is still executing — POSIX requires init to have completed. A proper fix needs a wait mechanism (tri-state flag), not just locking.
  • B2  pthread_key_delete leaves dangling nodes in other threads' key lists. It frees each pthread_key_data (linked into both the key's dlist and the owning thread's slist) without unlinking from the thread lists — the next pthread_getspecific() on any key by an affected thread walks freed memory. Fix requires storing the owning thread in the entry so delete can unlink, and it constrains any future lock-free getspecific design.
  • B3  poll() on a drained, at-EOF TCP socket blocks the full timeout. EOF/error state is only reported by the POLL_UPDATE pass; no k_poll event captures it. A socket that hit EOF before poll() was called (recv queue drained, cancellation already consumed) waits the entire timeout before update reports POLLIN|POLLHUP. Prepare should return -EALREADY when sock_is_eof()/sock_is_error() — which would also unlock the poll timeout fast-path below.

06Highest-value remaining opportunities

  • poll() timeout fast path enabled by an EOF/error-aware prepare (fixes B3, then legally skips the N×(lookup + mutex pair + 2 ioctls) update pass on quiet timeouts — the single biggest multiplexing win; busy-poll loops would roughly halve in cost).
  • TCP send single-copy scheme — refcount-share the send-queue net_bufs into wire segments for the no-retransmit case; eliminates one allocation and one full payload copy per segment.
  • Direct (non-variadic) poll prepare/update vtable ops — the two va_list ioctl dispatches cost ~250 instr of the 1069-instruction single-fd poll; optional typed function pointers in fd_op_vtable would remove them compatibly.
  • Absolute-timeout direct-to-ticks conversion across pthread/sem/mq timed waits — one conversion instead of three, and removes the sub-millisecond early-wake conformance defect.
  • pthread_getspecific redesign paired with the B2 fix — the two must be designed together.
